# Per-account self-service policy

Hosts can register a scoped `IHelloAccountPolicy<TProfile>` to evaluate current account data. `GetPermissionAsync` controls visibility and edit access for username, email, phone, profile, password and account deletion. Without a policy, the existing self-service behavior remains enabled. UI settings still impose their own restrictions. Failures returned by the policy fail closed.

The UI calls `GetProfileFieldAccessAsync` for individual fields, rendering visible non-editable fields disabled, and checks submitted names with `CheckProfileFieldsAsync`. `CheckProfileChangeAsync` must compare the proposed profile with the current account for every protected property, including fields not present in the built-in UI: headless callers can submit a full profile. Do not rely on hiding controls as authorization. Hello checks policy again on protected mutations and on both halves of phone binding, password and deletion step-up; a policy change during a challenge can therefore deny completion. The host must enforce the same rules in its own APIs and any direct Identity calls.

Hello's self-service password reset applies the policy after the Identity password-reset proof has been validated through the registered password validator. Trusted host-owned access recovery or direct administrative Identity operations are separate flows. Custom Identity credential implementations must invoke the registered password validators after validating reset proofs or enforce equivalent rules; merely registering a custom service does not make it safe.
